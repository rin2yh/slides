# 一覧ページへのデッキ追記

サイトのトップ（`https://<owner>.github.io/<repo>/`）は `site/index.html` そのもの。CI（`.github/actions/build-decks/action.yml`）はこれを `dist/index.html` にコピーするだけで、一覧の中身には一切触らない。

つまり **`site/index.html` を編集しない限り、デッキをいくらビルドしてもトップからは辿れない。** ここが抜けやすいので、デッキを足したら必ずこの追記までやる。

一覧はかつてスクリプト生成だったが、`slides/*.md` を舐めて HTML を組み立てる仕組みは意図的に捨てて手書きの静的ページに戻した経緯がある（`refactor: write the deck list by hand, let CD just copy it`）。**生成スクリプトを復活させたり、`<ul>` 全体を作り直したりしない。** 足すのは `<li>` 1 行だけ。

## 手順

### 1. デッキの実体を確認する

`slides/<name>.md` が存在することを確かめる。`<name>` はそのまま公開 URL のディレクトリ名になる（CI が `dist/<name>/index.html` を吐く）ので、リンク先を推測で書かず、必ず実ファイル名から取る。

### 2. frontmatter から title と date を引く

```yaml
title: Javaなしで安全に使えるPlantUMLビューア「pumlv」
date: 2026-07-29
```

- **title** はそのまま使う。一覧用に言い換えたり短縮したりしない。デッキの `<title>` / OGP と一覧の表示がズレると、SNS から来た人が同じ発表だと分からなくなる
- **date** は発表日。Marp も CI も読まない、この一覧のためだけに置かれているフィールド

`date` が無い、または `2026-01-01`（テンプレートの初期値）のままなら、そこで止まってユーザーに発表日を聞く。憶測の日付を入れると並び順が壊れ、あとから直すのが面倒になる。

### 3. `<li>` を 1 行足す

`site/index.html` の `<ul>` の中に、この形で 1 行入れる。インデントは半角スペース 6 個。

```html
<li><a href="./pumlv-go/">Javaなしで安全に使えるPlantUMLビューア「pumlv」</a><time datetime="2026-07-29">2026-07-29</time></li>
```

- `href` は `./<name>/` — **末尾スラッシュあり、`.html` は付けない**（実体は `dist/<name>/index.html`）
- `<time>` は `datetime` 属性と表示テキストの両方に同じ `YYYY-MM-DD` を書く
- `<a>` と `<time>` の間に改行や空白を入れず、1 行に収める。`time { display: block }` が効いているので日付は勝手に改行される

**改行を挟まない理由**：既存の行がすべて 1 行スタイルなので、ここだけ多行にすると差分が読みづらくなる。周りに合わせる。

### 4. 並び順を保つ

**日付の新しい順（降順）。** `<ul>` の先頭が最新。

- 追加するデッキが既存のどれより新しければ `<ul>` の直後
- そうでなければ、自分より古い最初の行の**上**に入れる
- 同じ日付の行がある場合は、新しく足すほうを上に置く

並べ替えのために既存行を動かす必要はまずない。既存の順序が崩れているのに気づいたら、追記とは別に指摘する。ついでに直すと差分が「1 行追加」でなくなり、レビューしづらくなる。

### 5. 確認する

```bash
git diff -- site/index.html
```

- 追加が `<li>` 1 行だけになっているか（インデントや既存行の空白が巻き添えで変わっていないか）
- `href` の `<name>` が `slides/<name>.md` と一致しているか
- 日付が降順のままか

ビルドは不要。CI がコピーするだけなので、`mise run build` を回して確認する必要はない。

## HTML エスケープ

title に `&` `<` `>` が含まれるときだけ `&amp;` `&lt;` `&gt;` に直す。日本語の `「」` や `・`、絵文字はそのままでよい（ファイルは UTF-8）。

frontmatter が `title: Go & Rust の比較` なら、`<li>` 側は `<a href="./go-rust/">Go &amp; Rust の比較</a>`。すでにエスケープ済みの文字列を二重にエスケープしない（`&amp;amp;` になってしまう）。

## 複数デッキをまとめて足すとき

1 件ずつ手順 2〜4 を回し、最後にまとめて `git diff` を見る。全部の日付を先に集めてから降順に並べたほうが、挿入位置を何度も探し直さずに済む。

## よくある落とし穴

- **すでに載っているデッキを二重に足す** — 追記前に `<ul>` 内を `<name>` で検索して、同じ `href` が無いことを確かめる
- **`dist/index.html` を直接いじる** — `dist/` は gitignore 対象のビルド成果物。編集しても次のビルドで消える。触るのは `site/index.html` だけ
- **README の例をそのままコピーする** — README の `<li>` は `go-coverage` の例示で、実在するとは限らない。`slides/` の実ファイルから引く
- **`<style>` や `<h1>` を「ついでに」整える** — 一覧の追記は 1 行差分で終わるのが正しい。見た目の変更を頼まれたなら、それは別の作業として分ける
